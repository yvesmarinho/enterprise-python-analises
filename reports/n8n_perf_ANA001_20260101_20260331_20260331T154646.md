| Hipótese | Evidência | Status |
|----------|-----------|--------|
| Fila de execução N8N saturada | 2,3 exec/s entrada; concorrência padrão N8N = 5–20; fila não instrumentada | ⚠️ **HIPÓTESE PRINCIPAL — NÃO CONFIRMÁVEL com métricas atuais** |

## 5. Lacunas de Instrumentação Identificadas

| Lacuna | Impacto | Ação Necessária |
|--------|---------|----------------|
| `n8n_queue_depth` — profundidade da fila de execução N8N | Não é possível confirmar hipótese de fila saturada | Habilitar métricas de queue no N8N (`QUEUE_HEALTH_CHECK_ACTIVE=true`) |
| `n8n_concurrency_*` — execuções simultâneas ativas | Não sabemos se workers estão saturados | Expor via endpoint `/metrics` (N8N >= 0.214) |
| Tempo de início (wait time antes de executar) | Latência percebida pelo usuário não medida | Adicionar log estruturado de `waitDuration` por execução |
| `node_memory_*` do wf001 | Sem dados de memória do host | Corrigir label `instance` no scrape config Prometheus |
| `instance` relabeling no exporter N8N | 0.0.0.0:5000 vs wf001 — duplicação de dados | Adicionar `relabel_config` com `replacement: wf001` |
| `n8n_workflow_execution_duration_seconds_bucket` — sub-100ms | Não mensurável abaixo de 100ms | Adicionar buckets: `0.005, 0.01, 0.025, 0.05` |
| PostgreSQL query latency | Não monitorado | Ativar `pg_stat_statements` + `postgres_exporter` com queries stats |

## 7. Resposta à Pergunta Original

> "Qual é o ofensor do desempenho do N8N?"

**Resposta baseada nos dados:**

1. **O ofensor de volume é `121Labs PABX call-analytics`** — 429K execuções em 90 dias, picos de 8.400/hora. Não é lento individualmente, mas domina a fila do N8N durante o horário comercial.

2. **O segundo ofensor é `hub-whatsapp-api-gateway-evolution-api`** — gateway WhatsApp via Evolution API com 84K execuções desde 04/mar. Verificar se o volume é esperado e se há rate-limiting adequado.

3. **A lentidão percebida provavelmente é tempo de fila** — os workflows completam em < 100ms cada, mas se a fila tem 500+ entradas aguardando durante o pico, o tempo de espera pode ser de minutos. Esse dado não está instrumentado atualmente.

4. **O hardware não é o gargalo** — CPU em 1–3% confirma isso. O problema é de capacidade lógica do N8N (workers, fila, banco de dados).
